01 / OVERVIEW

核心作用:它在解决什么问题

免费代理散落在各处:Telegram 频道里的一条条订阅链接、GitHub 代码仓库里的节点分享、机场网站的免费套餐。手动收集费时费力、质量参差、隔天就失效。Aggregator 把「找 → 验 → 洗 → 转 → 存」整条链路自动化,产出稳定更新、格式齐全、按质分组的订阅源。

🕷 多源爬取

Telegram 频道、GitHub 多模式代码/Issues 搜索、Gist 网页搜索、Google / Yandex 搜索、任意网页、自定义 Python 脚本插件,统一调度。

🔍 两层验证

订阅层:HTTP 拉取订阅链接,按流量余量/有效期门槛筛选;节点层:内置 mihomo 内核真实拨号测延迟。两层都通过才推送——「订阅能打开」和「节点能上网」是两件事。

🌐 本地代理友好

配置 crawl.proxy 后:探活通过则所有出网请求优先走代理,代理传输失败自动回退直连;连本机控制器(127.0.0.1)的请求永远直连,不被代理转发。

🔄 格式转换

通过内置 subconverter 把同一份节点池转换为 Clash、mixed(Base64 订阅)、SingBox 等格式;转换结果为空时保留远端旧文件并明确报错,不会把空内容推上去。

💾 灵活存储

结果推送到 GitHub Gist、PasteGG 等云端剪贴板,得到稳定的订阅 URL;也可存本地文件,完全自主。

🏷 分组管理

不同来源的节点可打上不同标签推送到不同分组(如 premium / free / backup),每组独立转换、独立存储。

举例 · 一句话理解 你在客户端里填一个 Gist 订阅 URL,每天早上自动多出几十个「昨天验证还活着」的免费节点——这背后就是 Aggregator 定时跑完一整趟流水线的结果。
关键认知 · 两种「不可用」不是一回事 订阅不可用(来源挂/流量耗尽/cookie 失效)是数据问题,该订阅被丢弃或冷却;而控制器不可用(mihomo 没起来/端口冲突)是验活设施问题——此时节点既没被判活也没被判死,程序会跳过发布并保留 Gist 上的旧文件,不会把几百个节点误判成全灭、更不会清空订阅池。日志里看到 ControllerError 或 controller did not become ready,先查验活环境,别怀疑节点。
02 / ARCHITECTURE

设计架构:五段流水线,一个入口

整个项目是一条单向数据流水线:爬取源产出原始订阅链接,逐级加工为可用节点,最终推送到存储。所有模块都在 subscribe/ 目录下,纯 Python 实现,Clash 与 subconverter 以预编译二进制形式内置,开箱即用。

数据来源加工环节
① 爬取 Crawl
TG / GitHub / Gist / Google / Yandex / 页面 / 脚本 → 提取订阅链接与散节点
→
② 注册 Airport
对机场站自动注册账号、领免费套餐、换取订阅(airport.py)
→
③ 聚合 + 验活 Clash
独立端口控制器,内核真实连通测试,按延迟 / 倍率过滤(clash.py)
→
④ 转换 Subconverter
按分组转换为 clash / mixed / singbox 等格式;空产物拒绝推送(subconverter.py)
→
⑤ 推送 Push
仅推送验活后确认可用的来源,一次内存写入订阅池(push.py)

03 / PROTOCOLS

代理协议对比:怎么选、怎么取舍

README 声明支持的核心协议为:VMess、VLESS、Trojan、SS、SSR、Snell、Hysteria、Hysteria2、TUIC、AnyTLS、HTTP、SOCKS;subscribe/outbound/ 中还有 Mieru、SSH、WireGuard、OpenVPN 等扩展校验器。协议没有绝对优劣,差别在于「伪装能力、传输性能、客户端生态」三个维度的取舍。

协议传输基础伪装 / 抗封锁性能生态与客户端一句话定位
SS
Shadowsocks		TCP弱 — 加密流量特征明显,易被主动探测轻量、延迟低极广,几乎所有客户端老牌轻量之选,部署最简单
SSRTCP + 混淆中 — 在 SS 上加协议/混淆层,但项目已停更略高于 SS逐渐萎缩历史兼容用,新部署不推荐
VMessTCP(TLS 可选)中 — 自定义加密协议 + 时间戳校验加密层较多,开销偏大V2Ray 生态核心,支持广V2Ray 家族经典协议,成熟稳定
VLESSTCP(TLS/Reality)强 — 本体不加密,配合 XTLS / Reality 可伪装成正常 HTTPS 站点轻量,开销小于 VMessXray 系客户端当前主流新部署,抗封锁首选之一
TrojanTLS强 — 流量就是标准 HTTPS,直连访问一个真证书网站接近原生 HTTPS广泛「长得像正经网站」的老牌强伪装
HysteriaQUIC / UDP中 — 伪装为 HTTP/3 流量极高 — 拥塞控制激进,差线路也快官方客户端 + 主流内核高丢包 / 跨洋慢线路救星
Hysteria2QUIC / UDP中强 — 完整 TLS 1.3 握手,认证更简洁极高,配置比一代简单得多主流内核均已支持新一代 UDP 高速协议的事实标准
TUICQUIC / UDP中 — 基于 QUIC TLS低延迟,多路复用主流内核支持QUIC 阵营的低延迟选项
SnellTCP中 — 私有二进制协议高效轻量Surge 生态专属苹果系 Surge 用户的私有选择
AnyTLSTLS强 — 专为消除 TLS-in-TLS 指纹设计接近直连较新,mihomo 等已支持针对流量指纹检测的新方案
HTTP / SOCKS5明文 TCP无 — 无加密,内容可被直接审阅零开销通用标准只适合内网、本机中转等可信链路
举例 · 典型搭配 机场订阅大多是 SS / VMess / Trojan;自己搭新服务器优先 VLESS + Reality 或 Hysteria2;网络对 UDP 限速严重时退回 Trojan;只在本机 / 局域网转发用 SOCKS5 即可。
注意 · ENABLE_SPECIAL_PROTOCOLS VLESS、Hysteria2 等较新的协议默认可能不参与收集,官方工作流通过环境变量 ENABLE_SPECIAL_PROTOCOLS 控制是否纳入特殊协议。
04 / CONFIGURATION

配置详解:填什么、哪些必须填、结果长什么样

process.py 的一切都由一份 JSON 配置文件驱动,配合环境变量提供凭证。先理解一条「名字链条」,配置文件就读懂了一半:

sites[].push_to
每个订阅来源声明「我要去哪个分组」
→
groups.分组名.targets
分组声明「我要产出哪些格式,存到哪个存储项」
→
storage.items.存储项
存储项声明「最终写到哪个 Gist / 文件」
举例 · 名字链条串起来 站点 A 写 "push_to": ["premium"] → 分组 premium 写 "targets": {"clash": "premium-clash"} → 存储里要有 "premium-clash" 这个 item 指向你的 Gist 文件。三个名字(premium、premium-clash)必须对得上,缺一环节点就「流」不到终点。

4.1配置文件总骨架(process.py)

my-config.json —— 模板见 subscribe/examples/config.default.json{ "sites": [ ... ], // 已有订阅 / 机场站点(可自动注册) "crawl": { ... }, // 爬虫开关与各数据源配置 "groups": { ... }, // 输出分组、格式与归一化 "storage": { ... } // 存储引擎与存储项 }

4.3支持的平台与爬取源配置(crawl)

Telegram 频道

telegram.channels 里按频道名配置(支持任意公开频道,频道名即键),每个频道可配 include / exclude 关键词与 push_to 分组,靠公共频道网页版翻页爬取,无需 TG 账号。

GitHub

github.push_to 必填;内置 3 组搜索模式(v2board 精确 / 泛化 token / sspanel 短链),代码 + Issues 双通道;patterns 可自定义扩展。配合 GH_TOKEN 防限流。

Gist 源(双模式)

配了 GH_COOKIE 走网页搜索(按 Recently updated 排序,实测 36 个 gist→133 条订阅);没配则退回公开时间线扫描(/gists/public,命中率低)。patterns/pages/max_gists 可调;读取内容用 GH_TOKEN 或 PUSH_TOKEN 均可,无需额外权限。

Google / Yandex 搜索

默认关闭,设 "enable": true 打开;适合补充冷门源,但验证码风险高,建议给 exclude_sites 拉黑名单。

本地代理 proxy

配置项三项:enable 开关、address 代理地址(如 http://127.0.0.1:7897)、test_url 探活地址。启用后:爬取与订阅验证优先走代理,代理传输失败自动回退直连;本机控制器请求(127.0.0.1)强制直连。详见下一节的探活规则。

自定义页面 / 脚本插件

pages 支持 {page} 占位符批量翻页;scripts 指定 plugin 执行自写 Python 插件,任何「要登录 / 要签名」的站点都能接。

配置无歧义 · crawl.proxy 三个字段怎么填
字段填什么
enabletrue/false。关掉后一切走直连,即使你本机有代理
address本地代理的 HTTP 入口,必须带 http:// 或 https://。Clash Verge 默认混合端口多为 http://127.0.0.1:7897,v2rayN 多为 http://127.0.0.1:10809
test_url一个「代理正常情况下应该能访问」的地址。它会返回 200/3xx,或者 401/403/429(被拒但链路通),都算代理可用;默认 https://api.github.com/zen
举例 · 探活地址选错的坑(真实发生过) 早期把 test_url 设成 https://www.google.com/generate_204:代理转发正常,但该地址返回的是 204,被程序当成「非 200 = 代理不可用」,于是每次启动都打印 local proxy ... unreachable, fallback disabled——代理明明开着却整个关闭了回退。另一例:用 api.github.com/zen 时代理节点返回 403,同样被误判。现在两种状态都被正确识别为「代理可用」。选 test_url 的原则:挑一个代理通时一定返回 200 的稳定地址(如 https://api.github.com/zen 或 https://www.gstatic.com/generate_204)。
举例 · 为什么本机控制器必须强制直连 mihomo 内核只监听 127.0.0.1:9090。旧版代码用统一的 urlopen 请求它,而这个请求被 HTTP_PROXY 环境变量一起转发到了你的代理软件——代理没有 9090 这个上游,返回 502,程序把 502 当成「节点延迟测试失败」:357 个节点全部误判为死亡,但同一批节点用直连复测 21/21 存活。现在 httpclient 对 127.0.0.1/localhost 的请求一律绕过代理,这类「全灭误报」不会再把可用节点和订阅池清空。

配置无歧义 · 旧内容如何处理:默认「回收」,-o 才「只用新的」 命令行默认不加 --overwrite(Dockerfile 与官方 workflow 也已改为默认)。此时上一轮发布到 Gist 的文件不会被丢弃,而是被当作一个新的“订阅源”拉回来:新旧 URL/节点先去重 → 一起过订阅层验证 → 一起过节点层验活,存活的旧节点会出现在新文件里,死掉的自然淘汰。只有加 -o/--overwrite 才是“本轮结果整体替换”。

举例:昨天文件里有 41 个存活节点;今天只爬到 12 个新节点。不加 -o:昨天的 41 个 + 今天的 12 个一起去重验活,假设 20 个旧 + 8 个新存活 → 新文件含 28 个。加 -o:新文件只可能含今天这 12 个里存活的(8 个),昨天那 20 个活着的节点直接消失。定时任务追求“池子只增不减”,就用默认。
crawled-proxies.json(节点快照)有什么用?可以不要吗? 它是上轮验活存活节点的原始 YAML 列表。三个用途:① 审计——不用翻 Clash 配置就知道上轮具体哪些节点活过、延迟多少;② 给外部工具消费——Base64/URI 形态可直接喂给自建脚本或其他客户端;③ 调试对照——和分组文件对比,确认“发布内容 = 验活结果”。
对纯订阅用户确实用处不大,而且它是可选配置:把 crawl.persist.nodes 改成空字符串(或从 storage.items 删掉对应项)即可彻底关闭推送,不影响任何其他行为(本仓库 my-config.json 已默认关闭,远端 Gist 上的 crawled-proxies.json 也已删除)。注意:它是纯输出,没有任何机制会把它读回重新验活——关心旧节点持续可用性靠的是上面的 remains 回收。

4.6结果以什么形式存在

  • 每个「分组 × 格式」一个文件:如 free-clash 产出 Clash YAML、free-v2ray(mixed)产出 Base64 订阅文本、free-singbox 产出 JSON。文件名由 storage.items 里该 item 的 filename 决定,与格式不一定同名。
  • 云端后端 → 订阅 URL:推送到 Gist 后,该文件的 raw URL 就是订阅地址,直接填进 Clash / V2RayN / Shadowrocket 等客户端。
  • 本地后端 → 文件树:<LOCAL_BASEDIR>/<folder_id>/<file_id>,如 output/premium/clash.yaml。
  • 订阅池(仅存可用来源):crawl.persist.subscribe(默认 crawledsubs)保存的 JSON 只包含本轮验活确认产出过存活节点的订阅 URL;每一轮用内存中的本轮结果一次性写入,不再先从远端读回再覆写(旧实现读回 Gist CDN 缓存会把刚删掉的失效订阅又写回去)。若本轮验活因控制器故障中断,则整池保持不动并保留旧文件。
  • 节点快照(仅存存活节点):crawl.persist.nodes(默认 crawledproxies)保存的 YAML 只包含验活通过的节点,重复节点会自动合并并保留全部来源订阅记录。
举例 · mixed 与 v2ray 的差异(选错会推出空文件) 同一批节点(假定 41 个:31 个 trojan/vless + 10 个 HTTP):clash 输出 41 条完整节点; mixed(Base64 订阅)输出 31 条——因为 HTTP 代理无法用「节点链接」形式表达,这是格式本身的限制,不是丢节点;而 v2ray 目标在内置 subconverter 上可能产出 0 字节。现在空产物会被直接拒绝上传(日志 [ConvertError] empty output),Gist 上保留的是上一次的好文件,而不是空文件或 422 报错。实践中把 groups.targets 配成 "mixed" 而非 "v2ray"。
05 / HOW-TO

最佳实践:一步一步跑通

项目现在只有 process.py 一个入口。按下面 9 步操作,一次搭好可持续自动更新的代理池。每一步都标注了「为什么」。

5.1标准实践 · process.py 完整流水线(长期自动化)

1

复制默认配置作为起点

cp subscribe/examples/config.default.json my-config.json
为什么 默认模板包含全部字段及注释位,先跑通再裁剪,比从零写少踩 90% 的坑。
2

填 sites:喂给它已知的好源

有现成订阅就这样填(跳过注册,最省事){ "name": "my-airport", "subscribe": ["https://xxx.com/api/v1/client/subscribe?token=..."], "push_to": ["free"], "include": "香港|新加坡|日本", "exclude": "过期|官网|剩余", "rate": 2.0 }
为什么 include/exclude 在源头就过滤节点名,减少后续验活压力;rate 拦掉三倍率「刺客」节点。没有现成订阅就改填 domain,让注册器自动去注册领免费套餐。
3

配 crawl:打开你想要的爬取源

四路源:TG 频道 + GitHub 多模式 + Gist 扫描 + 本地代理"crawl": { "enable": true, "proxy": { "enable": true, "address": "http://127.0.0.1:7897" }, "telegram": { "enable": true, "pages": 5, "channels": { "oneclickvpnkeys": { "push_to": ["free"] }, "VmessProtocol": { "push_to": ["free"] } } }, "github": { "enable": true, "push_to": ["free"] }, // 内置3组搜索模式, patterns 可扩展 "gist": { "enable": true, "push_to": ["free"], "max_gists": 100 }, "google": { "enable": false } }
为什么 Google / Yandex 爬虫容易被验证码卡住,首跑就全开只会收获一屏报错;TG + GitHub + Gist 是产出最稳的三路,proxy 启用后它们全部优先走本地代理。记得导出 GH_TOKEN 防限流。
4

配 groups:决定产出哪些格式

groups 键名 = sites.push_to 里的分组名,要对应"groups": { "free": { "emoji": true, "targets": { "clash": "free-clash", "v2ray": "free-v2ray" } } }
为什么 targets 的键是 subconverter 的格式名,值是存储项键名——这就是 4.x 节说的「名字链条」中游,上下游必须同名。
5

配 storage:告诉它写到哪

engine 选 gist,items 里为链条终点准备同名存储项"storage": { "engine": "gist", "items": { "free-clash": { "username": "你", "gist_id": "...", "filename": "free.yaml" }, "free-v2ray": { "username": "你", "gist_id": "...", "filename": "free-v2ray.txt" } } }
为什么 一个 Gist 可容纳多个文件,按分组 × 格式各占一个文件即可;不想用云端就把 engine 换成 local,items 里填 folder_id/file_id。
6

设置凭证并小规模试跑

先小线程、长超时,验证链路通,再上强度# Windows PowerShell $env:PUSH_TOKEN="ghp_你的令牌" python subscribe/process.py -s my-config.json -n 16 -t 10000 # Linux / macOS export PUSH_TOKEN=ghp_你的令牌 python subscribe/process.py -s my-config.json -n 16 -t 10000
为什么 默认 64 线程对家宽与低配机器压力大,先 -n 16 -t 10000(10 秒超时)确认端到端能产出文件,再逐步加线程。常用参数:--check 只验活不推送、-m 1 只采集不发布(安全试跑,不碰 Gist)、--invisible 隐藏进度条。
7

看懂日志:三层健康信号

一次正常运行应有的三类关键行[CrawlInfo] local proxy is available / configured // ① 源层:代可用,爬取优先走代理 [TelegramCrawl] channel=xxx, pages=5, nodes=280 // ① 源层:每频道实际抓到几页、几个节点 [GithubCrawl] finished ... found 3860 subscriptions // ① 源层:候选订阅总量 [CrawlInfo] start to validate 2681 subscriptions // ② 订阅层:进入可用性验证的数量 [CrawlInfo] crawl finished, found 75 sites // ② 订阅层:通过验证的来源数 [Check] controller ready, group=[free], nodes=322 // ③ 节点层:mihomo 控制器就绪,开始测速 proxies check finished, total: 322, alive: 41, dead: 281 // ③ 节点层:存活统计 [UpdateInfo] published verified subscription pool: kept=N // ④ 发布层:仅可用来源入池 [PushSuccess] push subscribes information to gist ... // ④ 发布层:各格式文件已上传
为什么 四个层次(源→订阅→节点→发布)任何一层出问题表现完全不同,先定位层次再排查,能避免「节点全死」这种误判把可用池清空。
8

检查产出、客户端订阅

打开 Gist,确认 free.yaml 等文件已被更新且含有效节点;复制 raw URL 到客户端订阅。节点名带 emoji、地区、倍率,来自 rename 与 regularize 归一化配置。

为什么 验活只代表「运行那一刻能通」,免费节点衰减快,单次结果仅供验证链路,持续可用靠第 9 步的定时调度。
9

自动化:GitHub Actions 或本机定时

仓库自带 .github/workflows/process.yaml,fork 后只需填 Secrets# Settings → Secrets and variables → Actions: PUSH_TOKEN = ghp_xxx # secret SUBSCRIBE_CONF = https://.../my-config.json # secret,配置可托管在私有 Gist GH_TOKEN = ghp_xxx # 可选,提升爬虫额度 GH_COOKIE = xxx # 可选,gist 网页搜索用 # 或者本机 crontab,每天 8:00 跑一次: 0 8 * * * cd /path/to/aggregator && PUSH_TOKEN=ghp_xxx python subscribe/process.py -s my-config.json
为什么 配置文件放私有 Gist 用 raw URL 引用,敏感信息不进仓库;官方 workflow 每天定时触发(cron 05 03/11 * * *),订阅内容随之每日刷新,这就是「代理池」的自我维持。

5.3常见误区与故障速查(全部来自真实运行)

某轮「存活 0」别急着清池

先搜日志有没有 ControllerError / controller did not become ready / mihomo exited。有 = 验活设施故障,程序已自动跳过发布并保留旧文件;没有才是真的全军覆没。实例:某轮日志写 357 全灭,但同一批节点直连复测 21/21 存活,原因是控制器请求被代理转发拿到 502。

日志说代理不可用,但浏览器能上网

检查 test_url 是否返回非 200(204/302/403 都曾导致误判)。排除方法:手动 curl -x http://127.0.0.1:7897 <test_url> -o /dev/null -w "%{http_code}",只要不是连接失败(000),就该让程序把代理判为可用。实例:generate_204 返 204、zen 返 403,都曾让整个回退被关掉。

抓取 0 产出≠源失效

看每个源的计数行:TG 现在按频道打印 pages=..., nodes=...,能区分「抓到 5 页 280 个节点」和「频道_page 请求失败」。实例:早期版本用 t.me 首页一次探测失败就跳过全部频道,实际各频道页面都是通的。

推送 422 / 空文件

Gist 返回 missing_field: files 通常是转换产物为空(如 v2ray 目标对某些节点组合产出 0 字节)。现在空产物直接拒绝推送并 [ConvertError] empty output,Gist 保留旧文件。把 target 换成 mixed 即可。

订阅池「删了又回来」

旧链路每个环节都从远端读回再整池覆写,Gist raw 的 CDN 缓存(约 5 分钟)会把删除项带回来。现在池子由本轮内存状态一次性发布,看到 published verified subscription pool: kept=N 就是权威数字。

昨天活着的节点今天消失了

如果你用了 --overwrite(或用了旧版 Docker 镜像),上一轮文件里的节点不会被回收重验,只有本轮新爬到的参与——昨天存活的节点若今天没被任何源抓到就会丢掉。新版 Dockerfile / workflow 已默认不加该参数;本机手动跑也请不要加。实例:自由节点衰减快,取消回收后连续几轮文件节点数可能不升反降。

配置校验失败

python -m json.tool my-config.json 先验 JSON 语法;再检查「名字链条」:sites.push_to → groups 键 → storage.items 键是否全部对得上。
